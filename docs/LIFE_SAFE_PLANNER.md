# LIFE SAFE PLANNER — FOUNDER INTENT TO STRUCTURED EXECUTION PLAN

The Safe Planner is the fail-closed bridge between an authorized founder instruction and the
existing Autonomous Development Work Driver. It is not a second scheduler, task system,
repository operator, or free-running agent. MainAI remains canonical for goals, versioned
plans, tasks, jobs, approvals, checkpoints, recovery and verification. The Development
Operator remains the only repository-effect boundary.

## Source truth, authority and context

`MainAIGoal.original_instruction` remains the exact source instruction. Planner
interpretation, assumptions, unknowns, alternatives and provider contributions are derived
checkpoint evidence and never rewrite that field. Explicit founder requirements, decisions,
corrections and authorized goals can authorize planning. Preferences, suggestions,
hypotheses, AI interpretations, unknown or superseded statements cannot silently authorize
execution. Conflicting current authority produces `CONTRADICTION_UNRESOLVED`; materially
ambiguous scope produces `NEEDS_CLARIFICATION` with the smallest bounded question.

Planning refreshes an owner-scoped, bounded Active Context set anchored on the current
MainAI task. It records typed references, deterministic inclusion reasons and activation
paths rather than copying canonical messages, documents, Memory Threads or evidence. A
problem framing records known facts, assumptions, unknowns, constraints, prohibitions and
what would invalidate the framing.

## Deterministic safety boundary

A candidate contains stable step identities, dependencies, purpose, expected result,
governed capability, structured arguments, risk, expected evidence, verification effect and
failure behavior. Dependencies are deterministically topologically ordered and cycle
checked. Every step must resolve to the existing Development Operator registry. Paths are
validated against the authorized repository/worktree scope. Raw shell-shaped arguments,
unknown capabilities, remote push, merge, deploy, force-push, production mutation,
credentials and unbounded instructions fail closed.

Provider assistance is optional. A provider receives only redacted founder text, bounded
context references, capability vocabulary, prohibitions, limits and a strict output schema.
Its result is only a candidate: the same deterministic validation, approval and Work Driver
validation apply. Provider/model/version/role and accepted/modified/rejected disposition can
remain contextual evidence; model confidence is never verification. A tiny explicit local
recipe registry proves provider-independent planning without pretending to understand
arbitrary prose.

## Explainability, revisions and execution

The accepted-plan checkpoint explains source authorization, interpretation, framing,
ordered capabilities, verification obligations, alternatives, relevant strategy/lesson
references, provider participation, context membership and stop conditions. Plan identity is
a deterministic hash of the complete candidate. A revision references its predecessor and a
mandatory replan reason; old checkpoints and MainAI plan versions remain historical truth.

The accepted output is the Work Driver's native `DevelopmentPlan`; no manual translation or
planner repository call exists. Work Driver performs bounded control, Development Operator
performs actions, and MainAI verification and approvals remain separate gates. Capability
gaps are checkpointed with exact need and whether unrelated work can continue. LifeAI
self-work receives no special permission or verification bypass.

## Deferred

Global prioritization, provider/quota routing, specialist-team construction, unrestricted
natural-language execution, automatic capability installation, automatic strategy
activation/promotion, universal or multimodal ingestion, world-model planning, autonomous
PR creation, merge, deployment, production mutation, browser control, unrestricted terminal
access and reinforcement-style policy mutation remain outside this foundation.
