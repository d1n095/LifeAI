WHAT THE DURABLE COORDINATION IMPLEMENTATION ACTUALLY IS (read on this SHA)
====================================================================================
Two separate substrates with very different multi-instance safety:

A. RELATIONAL ROWS (agent_work_assignments, agent_scope_leases) -- shared across instances.
   * LEASES are genuinely DB-fenced: acquire/renew/take_over use `SELECT ... FOR UPDATE`, a
     per-assignment partial unique index (uq_agent_scope_leases_one_active_per_assignment),
     generation + staleness checks. Takeover requires staleness and bumps the generation in
     place; `expected_generation` makes double-takeover deterministic. -> CC5 PASS.
   * ASSIGNMENT CREATION duplicate-work prevention is a check-then-insert
     (is_duplicate_canonical_work SELECT -> add -> flush) with NO unique index: migration 0046
     creates ix_agent_work_assignments_owner_work_key(owner_id, canonical_work_key) NON-uniquely.
     The same migration DOES use a partial unique index for leases, so the pattern was known and
     simply not applied here. The create_work_assignment docstring's claim "in addition to the DB
     CHECK constraints -- defense in depth" is FALSE for duplicate work. -> CC1 (item 2).
   * STATUS TRANSITIONS (transition_status) read status in Python and issue an unconditional ORM
     UPDATE (no status-guarded WHERE, no version column), so two instances both drive one running
     assignment to a terminal state and both record a status_changed event. -> CC2 (items 3/6).

B. IN-MEMORY SERVICE SNAPSHOT (DurableCoordinationService) -- per process.
   Obligations/handoffs/provider-dedup live in Python instance attributes (_obligations,
   _by_canonical, _seen_event_ids, _provider_ingestion["processed_event_ids"]). persist_owner_ledger
   serialises the WHOLE service to one JSON blob in provenance["durable_coordination"] with NO
   version/optimistic-concurrency guard.
   * A second instance that started without instance A's obligation overwrites the blob wholesale
     -> lost update. -> CC3 (item 4).
   * Dedup is per-instance, so two instances (e.g. after simultaneous restart, both loaded the
     pre-event snapshot) each accept the SAME provider event_id and both act on it.
     -> CC4 (item 5).
