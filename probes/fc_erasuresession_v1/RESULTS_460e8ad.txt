====================================================================================
CONFIRMED DEFECT (reclassification of the prior fc_crossauth LOW/informational observation)
====================================================================================

WHAT:  An explicitly REVOKED Founder session can still satisfy account-erasure authority and
       drive an ACTUAL protected-data deletion, for the full life of the reauth receipt when a
       new operation is begun, and UNBOUNDED once an operation is already in flight.

RESPONSIBLE COMPONENT:
       account_erasure_receipt_session_current(p_owner_id, p_access_jti)
       backend/alembic/versions/0086_account_erasure_reauth_binding.py  (authoritative body;
       not redefined by 0088/0095/0097 — they only call it). It is the session-binding gate for
       account_erasure_begin_operation / _set_phase / _complete_operation and for
       personal_recall_erasure_current (the predicate every erasure-scoped grant delete consults).

ROOT CAUSE (two interacting facts):
  1. The helper decides "session still current" with:
         AND rt.created_at > u.sessions_valid_after          -- two STORED timestamps
     and it NEVER inspects refresh_tokens.revoked_at. The comparison is a pure function of
     stored values; it does not change as the wall clock advances (ES2 — proven with rows dated
     2020). The earlier claim that the window "closes the next second" was FALSE.
  2. Every real revocation primitive sets sessions_valid_after to the CURRENT SECOND truncated
     DOWN (to match the integer-second JWT `iat` check `iat <= sessions_valid_after`), and sets
     refresh_tokens.revoked_at on the revoked session:
         * reset_founder_password_with_token  (0095)  sessions_valid_after = date_trunc('second', clock_timestamp())
         * revoke_current_founder_sessions     (0095)  same
         * revoke_all_sessions_for_user        (app/token_revocation.py)  now = utcnow_seconds()
     If the revoked session's refresh row was created at any sub-second offset within that same
     second (created_at = S.xxx, sessions_valid_after = S.000), then created_at > sessions_valid_after
     stays TRUE after the revoke, and — revoked_at being ignored — the just-revoked session is
     still treated as a current session.

WHY `iat` IS SAFE BUT THIS IS NOT: the access-token check in app/deps.py compares integer
       seconds with `<=` (iat <= sessions_valid_after) and fails closed. The erasure helper
       compares a MICROSECOND created_at against the same second-truncated value with strict `>`,
       which is exactly the sub-second same-second window.

EVIDENCE (what each test proves on the exact SHA, using the REAL production functions):
  ES1  the REAL reset_founder_password_with_token revokes the session (revoked_at set,
       sessions_valid_after bumped), yet with a same-second created_at the helper returns TRUE.
  ES2  wall-clock independence: TRUE persists at +1s/+1min/years; the different-second (ordinary)
       revoke is correctly FALSE — the defect is strictly the sub-second same-second case.
  ES3  END TO END: under the revoked session a NEW erasure operation begins and a REAL
       personal_recall_grants row is DELETED and committed (protected data destroyed).
  ES4  mechanism matrix: the access-jti blocklist (single logout / family-reuse revocation,
       app.token_revocation.revoke_access_token) DOES close the gate; the sessions_valid_after
       bump used by reset / logout-all / revoke-sessions does NOT, in the same-second case.
  ES5  an already-STARTED operation continues under the revoked session even after the consumed
       reauth receipt is EXPIRED — the post-begin checks consult only session-currency +
       consumed_at, never the receipt lifetime. The exposure is unbounded for an in-flight op.
  ES6  survives a fresh DB session / process restart (the discrepancy is in committed rows).
  ES7  remediation is deterministic: revoked_at IS NOT NULL after every revocation, and the
       helper's EXISTS body PLUS `AND rt.revoked_at IS NULL` returns FALSE on the same rows.

EXPLOITABILITY / SEVERITY: reclassified from LOW/informational to MEDIUM (confirmed, real
       production paths, destructive capability). Preconditions bound attacker-driven abuse: an
       already-minted unconsumed ACCOUNT_ERASURE reauth receipt bound to a compromised Founder
       session, and the revoked session's refresh-token created_at falling in the same wall-clock
       second the revocation truncates to (the attacker does not control reset timing). The
       security-relevant failure DIRECTION is the concern: the system's own revocation primitives
       (password reset / logout-all / revoke-sessions), used specifically to terminate a
       compromised session, do NOT reliably cut off a destructive erasure — and an in-flight
       erasure is not cut off at all. Not attacker-reliable, but a real correctness/defense-in-depth
       defect in a destructive authority boundary, not a timing nit.
