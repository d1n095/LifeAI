OBSERVATION (low / informational, not a defect): account_erasure_receipt_session_current
validates a session via `rt.created_at > users.sessions_valid_after` and the revoked-access-token
blocklist, but does NOT inspect `refresh_tokens.revoked_at`. sessions_valid_after is truncated to
whole seconds while created_at keeps sub-second precision, so within the SAME wall-clock second as
a password reset (which revokes refresh tokens and bumps sessions_valid_after to the truncated
second), a just-revoked session's created_at can still be > sessions_valid_after and the erasure
session-binding check can still pass for that sub-second window. Practical exploitability is
negligible (same-second race; requires an already-minted, unconsumed reauth receipt from that very
session; the next whole second closes it), and every other session-validity consumer that compares
against an access-token iat uses <= and fails closed. Recorded for the builders as a minor
consistency nit (consider checking rt.revoked_at in receipt_session_current, or comparing with the
same <= second-truncation rule used for access tokens), not a release blocker.
